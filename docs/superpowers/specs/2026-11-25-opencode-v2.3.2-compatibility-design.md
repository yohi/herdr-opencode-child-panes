## 1. Goal and boundaries

PROJECT_GOAL: OpenCode V2.3.2で安全にSubagentをHerdr上に自動可視化する。
CURRENT_SCOPE: 同一Host・共有Server・複数Root Pane。
Superpowers First / OpenCode V2 Native First / TDD. Reuse the existing registry, layout, queue, lifecycle and tests. Support distinct roots on the same local server, and prevent duplicate management of one root. The deliverables are this design, a single implementation plan, source and tests, a bounded host acceptance record, and updated README/SPEC/install instructions. Completion is an Owner decision after real host acceptance; publishing is separately authorized.

Non-goals: V1 changes; remote server; GUI plugin; new daemon/server, event bus or IPC infrastructure; OpenCode core modifications; OMO-private APIs; unrelated refactoring or UI expansion. No session creation, removal, interruption, prompt submission or mutation by the visualization plugin. No operation on unrelated panes. No automatic review/correction loop or later task execution.

## 2. Decisions and alternatives

| Decision | Owner selection | Alternatives considered / tradeoff |
| --- | --- | --- |
| Q1 | B: daily usable V2.3.2 | A compatibility-only leaves safety blockers; C wholesale redesign is unnecessary. |
| Q2 | B: shared local server, multiple root panes | A dedicated server per root limits daily usage; C remote support expands trust and networking. |
| Q3 | B: Native TUI plugin, limited migration | A server plugin requires discovery of client ownership from server process; C hybrid introduces communication and synchronization. TUI owns local visualization and can reuse core. |
| Q4 | B: exclusive owner per server/root | A independent clients duplicate child panes; C manual enablement sacrifices automatic operation. |

The following are engineering proposals, not additional Owner decisions: prefer existing public APIs; investigate read-only attach via TUI router before retaining CLI attach; if necessary, use a local OS-backed exclusive lock rather than a new service. These are conditional on the feasibility gate, not established capabilities. File names and interfaces in the plan are provisional until feasibility is established. Any architectural deviation or reduced acceptance scope returns to Owner.

## 4. Architecture and functional contract

### 4.1 Client-local adapter

Each local Root TUI runs one Native TUI plugin instance (public @opencode/plugin/tui). It owns the subscriptions, local pane identity, ownership guard, event normalization and existing pane orchestrator. No new server plugin is necessary. Ensure legacy server entry/configuration cannot concurrently mutate Herdr for this feature; migrate configuration explicitly and document rollback. Do not assume a loader export key or config syntax until P01.

Use HERDR_ENV and HERDR_PANE_ID in the actual TUI process; absent/invalid prerequisites or disabled switch yield no mutations. Resolve the visible root with public router/session API plus Herdr attribution; require a real root (no parent), exact server and local Herdr instance, and verified pane identity. Revalidate at mutation boundaries, not just at setup. If the route changes, plugin unloads or identity/connection changes, revoke authorization, stop timers/queued new work and reconcile only proven managed panes. No action on an unrelated or re-used pane ID. On ambiguity, leave the pane alone, report degraded visualization and do not claim recovery. Existing child panes may be retained on normal dispose as in the baseline only if replacement owner cannot duplicate them; otherwise close only proven managed panes or block takeover. No timer persistence requirement.

### 4.2 Exclusive owner and passive children

Ownership key: verified Server Identity + Root Session ID, in a common local coordination scope covering all participating TUI processes. Include verified Herdr context for pane validation, not as a way to permit duplicate owners for the same server/root. A URL alone (aliases, service restart, wrong endpoints) is insufficient unless a fixed, proven canonical local endpoint contract rejects ambiguous cases. Validate server identity and lifecycle; never persist secrets as keys. One active owner maximum; distinct roots independent. Acquire atomically before mutations; a loser is viewer-only. Never steal from a live/unknown owner. Normal exit releases only after in-flight mutations are quiescent or fenced. Crash recovery requires proven stale-owner exclusion and no leftover duplicate pane; otherwise fail closed. An OS lock candidate must demonstrate process exclusivity and safe release; in-memory flags, shared JSON read/write, or check-then-create are not sufficient alone. Do not introduce a new daemon or network transport.

Every managed Child TUI is marked passive before its plugin starts (proposed environment marker, validate actual propagation and prevent inheritance into unrelated root launches); it must never split panes, even when displaying a nested child or navigating to a root. A manually opened non-root session cannot become a root manager. Verify the spawned pane and root attribution before attach/close/resize; only managed panes may be closed. Unknown ownership/identity, failed verification or unavailable dependency: no new automatic pane.

### 4.3 Safe attach

Only visualize existing sessions attributable to the owning root and expected server. Preferred feasibility candidate B: launch passive TUI without a missing-session-capable --session target, verify exact existing child via ctx.client.session.get and parent chain, navigate with public ctx.ui.router.navigate, then verify expected Herdr agent_session and authoritative session identity. Candidate A: keep CLI root flags only if actual pinned host provides an enforceable no-new-session contract, including deletion between lookup and use. Neither a preflight get nor a post-launch ID alone is sufficient. A home route must not submit any prompt or silently create a session; test behavior on deletion before/during navigation. Reject missing, foreign, recreated or unprovable targets and wrong endpoint. Roll back only the newly created, proven owned pane; no session mutation. If neither route meets this contract, block automatic attach and return to Owner. Never bypass with undocumented internal APIs.

### 4.4 Events and lifecycle

Retain v2-events normalization for session.created with explicit parent/location, real activity (execution/step/text/reasoning/tool starts), idle via session.status and deprecated session.idle, deletion; no raw busy as first activity, no V1 envelope guessing. Use authoritative location and ancestry; cross-location/workspace ambiguity stays fail-closed (cross-location expansion not required). Verify event visibility and ordering via P03; use current read-only state reconciliation where needed to prevent stale/replayed events, duplicates and lost deletion. Do not invent a durable replay guarantee. Background shell/subagent/compaction require correct observed activity/idle/reopen behavior, not new hooks by default.

Preserve actual registry states waiting_activity, spawning, attached, idle_pending, closing, reopenable, closed, ignored, failed and SPEC's capacity/reopen/close/tombstone semantics except explicitly superseded API and ownership boundaries. Creation after real activity only; idle closes pane, never session; reopen same child; delete terminal within the verified lifetime; stale events after reload must be checked against authoritative existence/ownership. Serialize mutations; maintain bounded close retries. Defaults: enabled, max 4 managed panes per owner, idle 10000 ms, initial split right main:right 2:1, subsequent vertical stacking with existing balancing, no focus steal, debug off. Preserve configuration compatibility where applicable. Redact credentials, query, fragment and secret-bearing paths from logs; do not pass secrets as argv or persist them. Child must use the same verified server/authentication without exposing credentials. Failures are isolated from OpenCode itself.

## 5. Reuse and change boundaries

Reuse: pane-orchestrator.ts, child-session-registry.ts, child-session.ts, async-queue.ts, direction-policy.ts, herdr-client.ts, config.ts, logger.ts, shell-quote.ts and existing tests unless a demonstrated contract gap requires a local change.
Bounded change candidates: index.ts, v2-plugin.ts (retire server mutation adapter for target), v2-events.ts, root-session-resolver.ts, ownership-resolver.ts, attach-launcher.ts, package.json/lock, CI and release controls. New adapter/guard modules only if needed for separable responsibilities. Preserve Node >=20 baseline, TypeScript ESM, npm, vitest, biome, tsc, tsup and zod. Pin official V2.3.2 type contract as dev-only when feasible; test actual packaged loader as well. No unsafe type suppression, agent config pollution or hand-edit of dist/CHANGELOG. Production deployment and publication blocked until acceptance and separate approval.

## 6. Feasibility gate (Phase 0)

Run only after separate Owner approval, in disposable same-host OpenCode v2.3.2 and Herdr environment with isolated state, test sessions, no production credentials or real work, known versions and cleanup. P01 loader and package entry; P02 local Herdr CLI/environment; P03 event delivery for child/descendant and lifecycle; P04 canonical server/root/pane attribution; P05 atomic ownership and crash/duplicate handling; P06 safe existing-only attachment including deletion race; P07 passive marker and recursion prevention. Record command, versions, setup, observed result and redacted evidence per probe as PASS / FAIL / NOT_RUN / BLOCKED; distinguish inference from observation. Do not run product mutations while feasibility is unresolved. Failure or missing authority blocks affected capability, not unrelated read-only work. Return to Owner rather than inventing a new architecture. A throwaway spike is not product code or formal acceptance.

## 7. TDD and acceptance

Phase 1: RED (expected failure demonstrated for new behavior) → GREEN → REFACTOR (only needed) with existing regressions. T01 official type contract; T02 event contract; T03 distinct-root isolation; T04 exclusive owner; T05 competing acquisition; T06 passive child; T07 missing session rejection; T08 deletion during attach; T09 wrong attribution; T10 idle/reopen; T11 terminal deletion; T12 unload/reload/crash; T13 Herdr failures; T14 secret hygiene. Reuse already sufficient passing regression tests; never force artificial RED for existing correct behavior.

Host acceptance (fixed host, OpenCode 2.3.2, Herdr version, package/build identity and scope; synthetic sessions, evidence recorded):
- AC-01 actual packaged loader; AC-02 activity-triggered pane creation; AC-03 correct existing session; AC-04 idle close and same-session reopen; AC-05 no resurrection after deletion.
- AC-06 distinct root isolation on shared server; AC-07 one owner with duplicate TUI; AC-08 no recursive child splitting.
- AC-09 no unintended session creation in missing/deleted/racing/wrong-target case; AC-10 background subagent/shell/compaction behavior; AC-11 no plugin session mutation.
- AC-12 npm run lint, typecheck, test, build (all pass, record skips; host-gated skips not acceptance); AC-13 disable/rollback safely, including legacy server entry non-concurrency.
- Preserve focus/layout/capacity, verify unrelated panes and sessions unchanged. Capture before/after authoritative session inventory for negative tests, including no new IDs and no reused target creation. Never count mocked responses as host evidence. If user actions are needed to create fixture sessions, those are authorized test harness actions, not plugin actions.

## 8. Completion and stop

Owner decides daily-use readiness only after applicable AC-01..13 pass on the fixed target and known restrictions are recorded. Release separately approved; existing v2.0.0 publication is not V2.3.2 proof. Use one bounded final code review if needed; do not start another review/correction cycle because of a new finding alone. Security, ownership or data-preservation blockers keep affected operations disabled; report evidence, residual risk, unapproved work and choices. At design/plan delivery, stop: no probes, installations, source edits, merge, release or follow-on execution without Owner authorization.
